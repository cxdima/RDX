# RDX Studio

A local, editable music-production workspace with an offline AI co-producer.
You describe what you want to hear — in ordinary words, or by humming it — and
RDX turns that into music you can play, edit and export. This is a working
development build, not a finished producer and not a replacement for Ableton.

## Open RDX

Double-click **RDX.command**. It starts the local service and opens the studio,
reusing a running instance when one matches and never taking over an occupied
port. Keep its terminal window open during the session.

## What you can ask for

RDX understands musical language rather than parameter names. It knows 28 sound
characters (warm, bright, huge, dreamy, wide, punchy, goosebumps and so on),
composable drum kits, chord progressions built from your humming, and five
production moves. Some things it can do:

- *"The lead sounds too harsh, warm it up."*
- *"Give me a kick pattern with a double clap."*
- *"Turn the humming I recorded into a chord progression on the strings."*
- *"Build this section up and let everything suddenly fade at the end."*
- *"Put a strong synth in with the melody and give it a flanger."*
- *"Make the bass darker and turn it down a bit."*

**When RDX cannot do something, it says so.** Ask for sidechain compression, a
vocoder, a tape stop or a third-party plugin and it will tell you it does not
have that and name the closest thing it does. It will not quietly substitute a
different effect and report success.

**RDX describes what it actually did, not what it meant to do.** The summary in
the chat is generated by comparing the project before and after, so it cannot
overstate a change. If the model's intent and the real edit disagree, you see
the real edit.

## Implemented

- **Instruments:** supersaw, saw, pluck, sine, sub, pad, strings, choir, bell,
  FM and a noise source for risers. All synthesized — good, but synthesized;
  the strings are a detuned ensemble with vibrato, not an orchestra.
- **Sound:** filter, resonance, envelope, three-band EQ, drive, echo, reverb,
  plus a motion section — chorus, flanger, phaser, auto-pan, stereo width and
  glide.
- **Drums:** kick, rim, snare, clap, closed/pedal/open hats, three toms, crash
  and ride, chosen one layer at a time or as a named kit, with accelerating
  snare rolls, crashes and fills.
- **Harmony:** hum a line and RDX works out whether you gave it chord roots or a
  melody, infers the progression and voices it with smooth voice leading.
- **Production moves:** buildup (with an optional cut at the end), drop,
  breakdown, fade and layer. Each expands into ordinary edits you can see and
  undo as one step.
- **Arrangement:** sections, duplication, resizing, reordering; track
  duplication, naming and protection.
- **Automation:** filter, resonance, level, pan, reverb, flanger and chorus.
- **Recording:** audio import, monophonic hum transcription, rhythm onsets.
- **Everything else:** playback with real meters, master compression and
  limiting, undo/redo, SQLite persistence, project archives, MIDI export,
  stereo WAV rendering, and a packaged Max for Live bridge.

## Model

The local base is `mlx-community/Qwen3-4B-Instruct-2507-4bit`, pinned to
revision `50d427756c6b1b2fe0c0a10f67fbda1fc8e82c1b`.

Adapter v2 was trained here — 500 iterations, 39 minutes, val loss 5.214 to
0.274 — and scores **14/22** against the base model's **9/22** on the held-out
benchmark, with unusable output collapsing from 10 cases to 1. It is **not
activated**: it does not clear the 0.7 gate in `rdx/promote.py`, and that gate
was left where it was rather than moved to fit the result. RDX currently runs
the base model. To use v2 anyway, the command is in Developer Operations; to
go back, delete `data/models/rdx-v2/approved.json`.

**The model does not hold the musical knowledge.** What "warm" means, what a
buildup is made of and what a double clap is all live in `rdx/musical/` as code
with tests asserting the musical result. The model's job is to recognise which
operation you mean and how strongly. That split is deliberate: knowledge in code
can be read, tested and corrected, and it cannot hallucinate.

The dataset is split by *phrasing family* — no way of asking for something
appears in more than one split — so the validation number measures new wording
rather than recall. Every example is executed against the real edit engine
before it is written, so the data cannot teach an operation that would fail.

The benchmark is 22 hand-written requests in the user's own phrasing, checked at
run time against the training data to prove none of them leaked. It scores
whether the right operation reaches the right target with the right settings,
and whether unsupported requests are declined rather than approximated. It does
**not** measure musical quality. Only listening does that.

## Verification And Limits

Backend tests cover the edit engine, protection, history, transcription, archive
round trips, proposals, bridge authentication, and the musical knowledge itself
— that four-on-the-floor lands on every beat, that a double clap is two hits a
thirty-second apart, that a snare roll accelerates, that voice leading glides
rather than leaps, that "warm" closes the filter, and that unsupported requests
raise rather than approximate. One test parses the TypeScript audio engine and
asserts its drum map is identical to Python's, so a pattern always reaches the
voice it was written for.

The Max device was built and opened through Live, but **a real Live API
handshake and transfer have never been confirmed**. Treat that integration as
experimental. It packages correctly against Live 12.4.5.

Live 12.4.5 does add `Track.insert_device`, so native Live instruments and
effects are reachable in principle — see [RDX_PLAN.md](RDX_PLAN.md). Writing
automation envelopes into Live is still not in the documented API.

Other current limits: 4/4 only; up to 24 tracks, 16 sections, 256 bars; one clip
per track and section; hum and rhythm analysis capped at 30 seconds; imports
capped at five minutes. No spoken instructions, no plugin hosting, no polyphonic
audio-to-MIDI, no sidechain compression, no native Ableton automation writing,
no bidirectional Set synchronisation, and no perceptual mastering judgement.
WAV rendering is in-memory, so long arrangements need more memory. There is no
cloud service and no telemetry.

## Moving RDX to another Mac

**This repository has no remote. Every commit exists only on the machine it was
made on.** Before wiping or retiring a machine, either push it somewhere or copy
the whole folder — a fresh `git clone` from nowhere will not save you.

What Git carries: all source, tests, docs and configuration. What it does not,
because `.gitignore` excludes them: `data/` (2.1 GB of model weights, the
adapters, your projects and recordings) and `artifacts/`.

```sh
# 1. On the old Mac — take everything, including the ignored data
rsync -a --exclude node_modules --exclude .venv ~/Dev/RDX/ /Volumes/Drive/RDX/

# 2. On the new Mac — tools first
xcode-select --install
/bin/bash -c "$(curl -fsSL https://raw.githubusercontent.com/Homebrew/install/HEAD/install.sh)"
brew install ffmpeg node python@3.12

# 3. Restore, then rebuild the two environments Git does not carry
rsync -a /Volumes/Drive/RDX/ ~/Dev/RDX/
cd ~/Dev/RDX
python3.12 -m venv .venv && .venv/bin/pip install -e ".[train,dev]"
npm install && npm run build

# 4. Prove it before trusting it
npm test && npm run test:browser
```

If `data/models/qwen3-4b` did not come across, `.venv/bin/python
scripts/fetch_model.py` re-downloads the pinned revision. The adapters in
`data/models/rdx-v*` cannot be re-downloaded — they were trained here — so copy
them or plan to retrain.

**A machine with more memory changes what is worth doing.** Training was shaped
throughout by 16 GB: batch size 1, gradient checkpointing forced on, four LoRA
layers, and a run that competed with Ableton for RAM. On more memory, raise
`--batch-size` and `--layers` first and re-measure; the config in
`rdx/training.py` is all command-line settings for that reason. Check the peak
memory line in `data/training/train.log` before pushing further.

## Developer Operations

```sh
npm start                 # launch the studio
npm run build             # tsc -b && vite build
npm test                  # pytest
npm run test:browser      # playwright

.venv/bin/python scripts/build_training_data.py
RDX_ADAPTER=data/models/rdx-v2 .venv/bin/python -m rdx.training --iters 600
.venv/bin/python -m rdx.evaluate                                  # base
RDX_ADAPTER=data/models/rdx-v2 .venv/bin/python -m rdx.evaluate --adapter
RDX_ADAPTER=data/models/rdx-v2 .venv/bin/python -m rdx.promote    # activate
.venv/bin/python scripts/build_bridge.py
```

Python 3.12, Apple silicon, Node 24 and ffmpeg are the tested environment.
`RDX_DATA_DIR` isolates runtime data for tests; `RDX_PORT` picks the first port
to try; `RDX_ADAPTER` selects the adapter version, so an active one is never
overwritten. Do not run training and inference at the same time on 16 GB.

See [AGENTS.md](AGENTS.md) for the working guide, [RDX_PLAN.md](RDX_PLAN.md) for
architecture and continuation work, and [RDX_HANDOFF.md](RDX_HANDOFF.md) for the
project's direction. Model weights, audio, test artifacts and local databases
are intentionally excluded from Git.
